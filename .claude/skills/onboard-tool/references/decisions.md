# Onboarding decisions

The aspects to settle, in the order to present them: how to decide each one and what has gone wrong before. Option meanings and validation rules are in `docs/spec.md` §5.2; defaults can be left out of `tool.json`.

01. **Kind** (plain tool or tool-cache tool): a tool-cache tool when consumers use an official `setup-*` action. Check what that action does beyond installing (`setup-gcloud` logs in with the credentials of `google-github-actions/auth`, `setup-java` picks a distribution): dropping the action would lose it. Otherwise a plain tool, `addToPath` set to the folder holding the binary.
02. **Source**: prefer where upstream publishes (`github-releases`, `node-version`, `npm`, `pypi`, `docker`, ...). Anchor `extractVersion` so variant tags (`-slim`, `latest`) are dropped. Pitfall: among Docker registries only Docker Hub gives release dates, and not past 1000 tags (anonymous paging stops at page 10, as for `google/cloud-sdk`); `java-version` and `maven` give none.
03. **Version lines**: one per major consumers use, per minor only when they pin minors, `"*"` when the major changes often (gcloud: weekly). `from` is the oldest version consumers use in the line, or the current latest when they use `latest`. Leave `reason` out unless the line needs explaining (a pinned version, a `"*"` line chosen for a fast-moving major; it is required with `ignoredVersions`); then say why in generic terms, never naming repos, files or consumers, which change while the line stays.
04. **minAge**: keep the default; raise it when a bad release would hit every job at once and nobody needs it on day one. Leave it out when the check script reports no release date.
05. **Install layout**: for a tool-cache tool, copy what the `setup-*` action looks up, from its source: the name in its tool cache `find` call (`cacheFolder`) and its arch folder (`archFolders`, `aarch64` for Java). A mismatch makes the action download anyway.
06. **Setup action**: find the inputs that bypass the tool cache (`latest`, `check-latest`, ranges resolved online). Consumers pass the resolved version instead; say so in the `install.sh` header comment.
07. **Platforms**: check both Linux archives (amd64, arm64) exist upstream. One build per Ubuntu release only when upstream ships one (Python). macOS and Windows aren't covered.
08. **Scripts**: `install.sh` gets `VERSION`, `TARGETARCH`, `ARCH` (arch folder), `DEST` and a `download <url>` helper; `test.sh` gets `VERSION` and `TOOL_DIR` on a plain Ubuntu image, and checks the binary reports `VERSION` plus the companion binaries consumers use. `test.packages` only for runtime dependencies runners have. When upstream publishes checksums, `install.sh` checks the download against them: a rule, not a question.
09. **Retirement**: none at onboarding. When upstream releases often, give the yearly storage growth (archive size × releases per year × 2 platforms).
10. **Consumer usage**: the selector consumers will write (`<tool>@<major>`, or a bare `<tool>` for a `"*"` line) and the step for one of their jobs. Migrating consumers is not part of onboarding.
